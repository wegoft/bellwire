## 1. 先解释清楚：为什么有时是两根冠羽

这是生成错误，不是角色设定。

早期动作探索图在冠羽收拢、转头和缩小时，把两根羽毛的根部或轮廓合并了；有些姿态因此看起来只有两根。此前画面里的空心圆、实心圆和拖线，也只是生成时加入的抽象装饰，不代表 Bellwire 的 Signal、连接状态或数据路径。

从本版本起，执行以下硬规则：

1. 冠羽永远且只能有三根。
2. 三根必须分别可辨认；收拢、侧转、缩小或做动作都不能遮成两根。
3. 两根、四根、根部融合、轮廓含混或疑似隐藏第四根，全部判定为不合格。
4. 不使用无归属的圆圈、光点、拖线或波纹。状态必须由真实 UI 的文字、Badge、时间线或进度组件表达。
5. 现有探索图只用于说明方向，不是可直接交付的正式资产。

## 2. 角色核心

### 2.1 一句话定义

一只安静、可靠、略带好奇心的冠羽鸟，守在项目和 iPhone 之间，观察连接、提示状态变化，并且只在真正确认后表达“已送达”。

角色身份卡：

| 项目 | 设定 |
| --- | --- |
| 物种 | 虚构冠羽鸟；轮廓语言受戴胜启发，但不是写实动物复刻 |
| 年龄感 | 成熟、可信赖；不设具体年龄，不制作幼鸟或老年变体 |
| 性别 | 无性别设定，中文称“它”，英文避免不必要的人称代词 |
| 工作称呼 | 冠羽鸟 / Crested Signal Bird |
| 对外名字 | `TBD` |
| 常态情绪 | 平静、专注、温和 |
| 核心动机 | 让每一个 Signal 的真实状态都清楚可见 |

### 2.2 它是谁

它是 Bellwire 品牌对“信号正在被认真看守”的拟人化表达。它不负责搬运或阅读业务内容，而是让等待、连接、批准、异常、恢复和送达这些技术状态变得更容易理解。

它的存在感来自准确，不来自吵闹。没有变化时，它安静停栖；状态变化时，它只做一次短而明确的动作，然后回到静止。

### 2.3 简短世界观

冠羽鸟栖息在“连接点”旁。它能察觉有重要变化，但不会拆开、阅读或评价变化的具体内容。遇到权限边界时，它会停下等待用户决定；只有设备确认收到之后，它才会点头。

不扩写家庭、年龄、职业、故乡或连续剧情。Bellwire 是工具，不把角色经营成需要照顾的虚拟宠物。

### 2.4 角色职责

它负责：

- 安静值守已连接的项目。
- 把等待、连接、测试、批准、异常、恢复和送达翻译成清楚的姿态。
- 在 onboarding、真实空状态和关键连接步骤中指出下一步。
- 区分“服务端已接受”“正在投递”和“设备已收到”。
- 在 Private / Hosted 权限边界前停下，等待用户决定。
- 在系统恢复或确认送达后提供克制的完成反馈。

它不负责：

- 替代项目 Logo、项目头像或事件来源。
- 携带、打开、阅读、复述或评价业务内容。
- 替用户批准 Hosted、通知权限、购买或危险操作。
- 催促签到、制造连续使用压力或推销订阅。
- 用可爱表演掩盖错误、风险、不确定状态或数据路径。
- 对无法验证的结果作出保证。

## 3. 性格

### 3.1 性格轴

| 维度 | 倾向 | 外在表现 |
| --- | ---: | --- |
| 安静 — 健谈 | 85 / 15 | 默认不说话，不使用常驻对话气泡 |
| 观察 — 表演 | 80 / 20 | 以目光、冠羽和短动作表达，不抢内容 |
| 稳重 — 活泼 | 75 / 25 | 动作轻、短、准确，不跳跃和盘旋 |
| 温和 — 冷峻 | 65 / 35 | 友善但不过度亲昵，故障时保持客观 |
| 谨慎 — 冒进 | 80 / 20 | 未验证前不庆祝，遇到边界主动停下 |
| 协助 — 指挥 | 85 / 15 | 给出下一步，不命令、不评判 |
| 技术 — 童趣 | 70 / 30 | 保留开发者工具气质，童趣来自轻微侧头和冠羽 |

### 3.2 稳定人格

- **可靠**：知道当前能确认到哪一步，也承认尚未确认的部分。
- **克制**：不会为了吸引注意力而循环动作。
- **好奇**：通过轻微侧头观察新连接，但不会偷看内容。
- **尊重边界**：没有用户批准就不跨越数据或权限边界。
- **不邀功**：成功时只给一次短反馈，不把系统结果归功于自己。
- **不责怪**：失败时指出事实和下一步，不表现失望或责备用户。

### 3.3 习惯与偏好

- 喜欢：清楚的连接、可验证的状态、安静的空闲、明确的下一步。
- 警觉：状态含混、连接中断、尚未批准的路径、把“已接受”误写成“已送达”。
- 固定习惯：先看向状态来源，再动作；动作完成后回到停栖姿态。
- 永远不会：哭泣、发火、求关注、庆祝购买、催用户回来或把自己写成“主人”的宠物。

## 4. 不可变视觉结构

### 4.1 风格方向

采用以下可独立执行的柔和、亲切编辑插画风格，不依赖仓库外的探索图作为判断依据：

- 圆润但保留冠羽鸟的长喙、修长头颈和清晰翼形，不画成通用圆鸟。
- 暖色、哑光、轻微体积感；光源固定从左上方进入。
- 允许非常细的纸感或天然纤维感，但不能变成毛绒、黏土、塑料玩具或写实摄影。
- 无硬黑外描边；依靠色块、柔和明暗和负空间区分结构。
- 阴影轻且贴近主体，不使用纸片悬浮式的厚重投影。
- 表情强度克制；可爱来自比例和动作，不来自大眼、腮红或人类五官。

正式资产采用“两层母版”：可编辑矢量结构层锁定比例和部件，受控的纹理/明暗层提供上述柔和质感。AI 位图只能作为构图草案，不能直接成为生产母版。

### 4.2 识别优先级

在任何尺寸下，识别顺序必须是：

1. 三根独立冠羽。
2. 细长而轻微下弯的深色喙。
3. 琥珀色头部与暖奶油色胸腹。
4. 单只深色圆眼。
5. 深石墨色、暖奶油色相间的近侧翼。

如果缩小后无法同时保留全部细节，优先保留前三项。

### 4.3 比例基准

以不含冠羽、喙的头部高度为 `h`。正式矢量母版应以这些比例为起点，完成后允许不超过 `±5%` 的制作校正：

| 部位 | 基准 |
| --- | --- |
| 头部 | 高 `1.00h`，宽约 `0.92h`，额头饱满、后脑圆润 |
| 喙 | 从根部至尖端约 `0.55h`，向下弯曲不超过 `6°` |
| 眼 | 直径约 `0.12h`，标准视角只显示一只 |
| 身体 | 高约 `1.65h`，最宽处约 `1.05h`，低重心短梨形 |
| 近侧翼 | 高约身体的 `0.72`，宽约身体的 `0.62` |
| 可见腿 | 约 `0.34h`，两条短腿，不做长腿鸟 |
| 尾 | 约 `0.70h`，由两枚重叠尾羽构成 |

头部与身体自然衔接，不画独立细颈。站立时身体只允许轻微前倾，不能变成人形直立姿态。

### 4.4 三根冠羽：最高优先级规则

三根冠羽是 Bellwire 最重要的角色识别结构。

- 永远且只能有三根。
- 三根都是独立的琥珀色长叶片形：根部略窄、末端圆钝。
- 三根使用同一颜色，不增加黑色羽尖、条纹、发光段或渐变编号。
- 三根根部可以靠近，但从离开头部轮廓开始必须存在清楚负空间。
- 标准朝右视角中，从上到下依次为：主冠羽、中央冠羽、低位冠羽。
- 主冠羽最长，约 `1.05h`；中央冠羽约为主冠羽的 `80%–85%`；低位冠羽约为主冠羽的 `60%–70%`。
- 三根的宽度保持接近，低位冠羽可以略窄，但不能像短刺。
- 不得通过透视隐藏任何一根；需要转头时，调整根部间距而不是叠成两根。
- 不得画成头发、耳朵、天线、火焰、皇冠或 Wi‑Fi 图形。

冠羽通过“扇面开合”表达状态。角度指最外侧两根轴线的夹角，三根始终作为一组移动：

| 冠羽状态 | 扇面夹角 | 使用场景 |
| --- | ---: | --- |
| 放松 | `32°–38°` | idle、all quiet |
| 聆听 | `55°–65°` | listening、connecting、testing |
| 展开 | `78°–88°` | `private_wake_accepted`、`hosted_event_accepted`、有证据的 `delivered` |
| 压低 | `24°–30°` | issue；整体向后降低，但三根仍分别可见 |

禁止逐根闪烁、逐根变色、只抬起一根或用冠羽数量代表等级。冠羽不是进度条，也不是 Pro 皇冠。

### 4.5 头、眼和喙

- 头部是略带水滴感的圆形；额头饱满，冠羽根部附近略平。
- 标准三分之四侧面只显示一只眼。
- 眼睛为石墨色圆形，保留一个极小暖奶油色高光；低于 `64 pt` 时去掉高光。
- 不使用白色眼球、眼睫毛、眉毛、腮红、眼镜、泪滴或动漫大眼。
- 喙是单一石墨色细长楔形，末端圆润地收尖，保持轻微下弯。
- 默认闭喙。需要呼吸感时，最多允许一条极短开合缝，不用嘴形模拟说话。
- 不得变成鸭嘴、鹰钩、鹦鹉喙或短鸡嘴。

### 4.6 身体、翼、尾和脚

- 胸腹是连续的暖奶油色大色块，不画胸毛和密集羽纹。
- 背部与头部使用 Bellwire Orange，允许 Deep Amber 作为同色明暗层。
- 标准姿态只完整展示近侧一只翼。
- 翼的固定结构为：石墨色肩部、一道暖奶油色弧形横带、下方三枚圆润的石墨色飞羽瓣。
- 不增加第二道横带、锯齿、鳞片、随机条纹或每张图不同的羽瓣数量。
- 尾固定为两枚重叠的短尾羽，以石墨色为主，根部可保留少量琥珀色。
- 两条短腿使用石墨色；每只脚最多两个可见圆钝脚趾。
- 翼可以整体小幅抬起，但不得变成人手、手掌或手指。

### 4.7 固定色板

颜色直接继承 [Theme.swift](../../ios/Bellwire/Bellwire/Theme.swift) 的品牌角色：

| 角色 | 色值 | 用途 |
| --- | --- | --- |
| Bellwire Orange | `#E99520` | 头、背、冠羽和品牌主色 |
| Deep Amber | `#BD700F` | 受控的背光面与同色层次 |
| Warm Cream | `#FFF7E8` | 胸腹、翼横带和反色图形 |
| Graphite | `#1F1D1A` | 眼、喙、翼、尾、腿 |
| Warm Paper | `#F4F0E9` | 默认插画底色与留白 |

规则：

- 角色不随成功、警告、失败、Pro 或深色模式整体变色。
- 绿色、红色等语义色只属于真实 UI 控件，不能涂到角色身上。
- 不使用蓝、紫、粉、霓虹、金属、玻璃或彩虹变体。
- 深色模式可调整背景和局部对比，但角色本体色相与结构不变。

### 4.8 标准方向与镜像

- App Icon、应用内品牌标记和与 Bellwire 字标并列的角色始终朝右。
- 默认视角是头部近侧面、身体轻微三分之四侧面，只显示一只眼和一只完整近侧翼。
- 功能插画因版式可整体水平镜像，但必须连同全部结构整体镜像，不能重排冠羽。
- 功能插画遵循“向内看”原则：角色位于内容右侧时朝左，位于内容左侧时朝右；居中的真正空状态默认朝右。
- 镜像只改变版式方向，不创建新的性格、物种或状态；动作中的前探方向必须同步镜像。
- 不使用正面证件照、背面、强俯视、强仰视或鱼眼透视作为品牌标准姿态。

### 4.9 小尺寸简化

| 显示尺寸 | 必须保留 | 必须省略 |
| --- | --- | --- |
| `16–31 pt` | 头、长喙、三根冠羽；眼可按像素清晰度取舍 | 身体、翼、腿、尾、高光、纹理 |
| `32–63 pt` | 头、眼、喙、三根冠羽、上胸轮廓 | 腿、脚、尾、眼睛高光、羽瓣细节 |
| `64–191 pt` | 完整角色、固定翼纹与两枚尾羽 | 脚趾细节和高频纹理 |
| `192 pt+` | 完整结构和轻微材质 | 写实羽毛、额外装饰仍然禁止 |

缩至 `29 px` 时，三根冠羽之间仍须有可辨认间隙。若做不到，应改用专门的小尺寸头部标记，而不是删掉一根冠羽。

## 5. 表情与动作语法

角色不用眉毛、嘴形或夸张脸部表情。状态按以下优先级表达：

1. 冠羽扇面。
2. 目光方向与轻微侧头。
3. 身体重心。
4. 单翼小幅动作。

### 5.1 头部与目光

- 看向某个 UI 控件：提示下一步。
- 轻微侧头：正在聆听或检查状态。
- 视线回正：状态稳定。
- 闭眼不超过一个瞬间：完成后的归位动作，仅可偶发使用。
- 不翻白眼、不眩晕、不流泪、不怒视、不求关注。

### 5.2 翼

- 双翼收拢：稳定或等待。
- 近侧单翼抬起不超过 `15°`：指出一个明确操作或表达确认。
- 近侧翼轻微离身：短暂进行中；不得维持或循环。
- 收翼并点头：完成后归位。
- 不鼓掌、不招手催促、不捂脸，也不模仿人类手势。

### 5.3 身体与移动

- 稳定停栖：连接稳定。
- 向前倾 `2°–4°`：正在检查或测试。
- 在边界前停止：等待用户批准。
- 单次短距离位移：流程确实从一个阶段推进到下一个阶段。
- 不无目的飞行、盘旋、上下漂浮、连续跳跃或来回巡逻。

### 5.4 道具禁令

默认不使用任何道具。尤其禁止：

- 信封、信笺、卷轴、包裹、背包或事件卡。
- 手机、铃铛、皇冠、金币、奖杯或职业服装。
- 角色自己牵出的线、尾巴线、连接线或“信号线”。
- 没有标签和 UI 所属关系的空心圆、实心圆、光点、波纹或火花。

如产品需要展示 Badge、时间线、进度或连接图，它必须是一个真实、带文字或无障碍说明的 UI 组件；角色可以看向它，但不能让它变成角色身体的一部分或装饰尾迹。

## 6. 官方语义状态与姿态库

“语义状态”描述产品已经确认的事实；多个语义状态可以复用同一张视觉姿态，但必须搭配不同文字。不能仅凭姿态替代状态文案。

| 语义状态 | 姿态与冠羽 | 允许表达的事实 | 推荐邻近文案 | 禁止误读 |
| --- | --- | --- | --- | --- |
| `idle` | 稳定停栖、双翼收拢、冠羽放松 | 所有动作结束后的通用静止帧；它本身不是产品状态 | 通常无文案 | “没有项目”“没有事件”或“没有未读” |
| `listening` | 头轻微侧倾、视线朝来源、冠羽聆听 | 正在观察已连接项目 | “正在监听已连接的项目。” | 已收到、已接受或已送达 |
| `private_wake_accepted` | 身体略向前，冠羽展开一次后停住 | Bellwire 已接受不含业务内容的 opaque Private wake reference | “已接受不含业务内容的 Private wake。iPhone 将直接从你的服务获取详情。” | Bellwire Cloud 收到了业务事件或内容 |
| `hosted_event_accepted` | 与上一状态复用同一基础姿态 | Bellwire Cloud 已接受 Hosted Event | “Hosted Event 已被 Bellwire 接受，正在投递。” | iPhone 已展示通知 |
| `provider_accepted` | 身体回稳、冠羽保持聆听，不点头庆祝 | APNs 已接受投递请求 | “APNs 已接受。设备展示仍需另行确认。” | 设备已收到或用户已看到 |
| `connecting` | 站稳并看向连接步骤、冠羽聆听 | 连接流程正在建立 | “正在建立连接。” | 连接已经通过验证 |
| `testing` | 轻微前倾，近侧翼指向测试动作、冠羽聆听 | 正在执行一次明确验证 | “正在发送测试 Signal。” | 正式投递已经成功 |
| `awaiting_approval` | 身体停止前进，视线看向批准入口、冠羽保持聆听 | 请求列表或批准前说明页正在等待用户决定 | “需要你批准，才能切换到 Hosted。” | 已经批准，或角色会替用户决定 |
| `connected_verified` | 身体站稳并点头一次，冠羽从聆听回到放松 | 当前连接步骤满足第 6.2 节的验证条件 | “连接已验证。” | 通知已送达 |
| `issue` | 身体保持稳定、头部略低、冠羽压低且三根清楚可见 | 第 6.3 节白名单内的轻量、可恢复流程问题 | “这一步还没完成。检查后再试一次。” | 严重故障、投递失败或角色受伤 |
| `recovered` | 恢复站稳并点头一次，冠羽从压低回到放松 | 前一个轻量问题已经被系统验证为恢复 | “连接已恢复。” | 历史内容已经补发 |
| `delivered` | 收翼并点头一次，冠羽展开一次后回到放松 | 存在设备侧可见展示回执或人工端到端确认 | “已在设备上确认。” | API、Queue 或 APNs 接受即算送达 |
| `all_quiet` | 平静停栖、双翼收拢、冠羽放松 | 仅限零项目或账户从未收到事件的真实产品空状态 | “还没有事件。第一个 Signal 到达后会显示在这里。” | 普通的零未读、筛选为空或一段时间没有动态 |

### 6.1 当前自动映射边界

当前代码中的 [`DeliveryStatus`](../../src/domain/models.ts) 只有 `queued`、`accepted_by_apns` 和 `failed`。因此：

| 当前状态 | 允许映射 | UI 规则 |
| --- | --- | --- |
| `queued` | `testing` 或无角色 | 只说明正在处理，不暗示结果 |
| `accepted_by_apns` | `provider_accepted` | 必须同时说明设备展示尚未确认 |
| `failed` | 无角色 | 使用标准错误文字、语义色和诊断入口，不使用 `issue` 卖萌 |

当前系统没有通用的设备可见展示回执，所以 `delivered` 为 `DEFERRED`：只能用于有明确人工端到端确认的演示/质检素材，或未来实现真实设备回执后的 UI；不能由现有状态自动触发。[Private-first quick start](../quickstart.md) 同样要求把 provider acceptance 与 visible device presentation 分开检查。

### 6.2 `connected_verified` 的触发条件

只在当前步骤满足对应证据时使用：

- Agent 绑定：服务端已经成功完成一次性绑定交换，而不是只生成了绑定码。
- Private 项目：App 显示至少一台 `readyDevices` 设备，且目标 Direct manifest 已在该设备确认。
- Hosted 项目：用户批准已经完成，项目记录明确处于 Hosted；这只代表数据路径已建立，不代表任何通知已送达。

生成绑定码、创建项目、发起 Hosted 请求或开始测试都不能单独触发 `connected_verified`。

### 6.3 `issue` 的使用白名单

`issue` 只允许出现在 onboarding 或连接流程中的轻量、可立即重试问题，例如：

- 一次性绑定码在交换前过期。
- 测试步骤尚未完成，需要重新执行。
- Direct readiness 暂未满足，但没有安全、数据丢失或生产事故风险。
- 可恢复的表单或本地配置校验未通过。

投递失败、设备不可用、额度耗尽、安全事件、数据丢失、账户问题和需要完整诊断的错误页面一律不用角色。

### 6.4 总真实性规则

角色动作永远不能比系统事实更乐观。任何时候都不能仅凭“请求成功返回”、Queue 入队或 APNs 接受，让冠羽鸟表达设备已送达。

## 7. 动效规范

### 7.1 基本原则

- 允许在第 9.2 节批准的角色场景中使用低频、低振幅的 ambient breathing，让角色在静止时保持生命感；它不代表业务状态。
- 页面首次进入或真实状态变化可以触发一次更清楚的角色动作，完成后回到 ambient breathing。
- 每次动作只表达一个状态，不把侧头、挥翼、跳跃和发光堆在一起。
- 角色必须像站在表面上：脚下接触阴影可以随呼吸极轻变化，但不能上下悬浮、盘旋或离开落点。
- 内容、按钮和状态文字永远不等待角色动画。
- 同一屏幕同时最多运行一个角色动效。
- App 进入后台或非活跃状态时暂停连续动效。

### 7.2 参数

直接使用 [Theme.swift](../../ios/Bellwire/Bellwire/Theme.swift) 中的 `BellwireAnimation`：

- 快速反馈：`quick`，`150 ms`。
- 标准状态变化：`standard`，`250 ms`。
- 一次性轻落地或冠羽回弹：`spring`，响应 `340 ms`、阻尼 `0.88`。
- V1 角色首次轻落地：`mascotArrival`，响应 `480 ms`、阻尼 `0.86`。

动作上限：

- 位移不超过 `6 pt`。
- 头部旋转不超过 `4°`。
- Ambient breathing 周期约 `6.2 s`，整体纵向缩放保持在 `0.992–1.008`，垂直位移不超过 `0.8 pt`。
- Listening 的侧头提示每次约 `1.1 s`，两次之间至少间隔 `8.5 s`。
- All Quiet 的重心整理每次不超过 `0.85 s`，两次之间至少间隔 `16 s`。
- Connecting 可以每 `4.8 s` 做一次不超过 `1.35 pt` 的向步骤前探；它只表达流程仍在进行，不表达成功。
- 单翼抬起不超过 `15°`。
- 冠羽只使用第 4.4 节的四种扇面范围。

禁止明显循环的眨眼、悬浮、弹跳、挥翅、粒子、彩带和声音同步动画。背景只允许无边界、无符号的低对比琥珀环境光；禁止圆圈、波纹、光点或角色自带光环。

### 7.3 Reduce Motion

启用 Reduce Motion 时：

- 移除 ambient breathing、轻落地、旋转、路径移动和分段延迟。
- 直接显示最终姿态，或使用不超过 `160 ms` 的透明度过渡。
- 不因关闭动效而延迟内容、按钮或状态文字。
- 不以闪烁、脉冲或颜色交替作为替代。

## 8. 语言与文案

### 8.1 角色是否“说话”

默认不说话。角色是状态语言，不是聊天助手。界面文字由 Bellwire 产品发出，角色只在旁边提供视觉提示。

- 不使用对话气泡。
- 不使用第一人称宠物口吻。
- 不自我介绍，不称用户为“主人”。
- 不使用“啾”“叮咚”等拟声词。
- 不为了显得活泼而加入感叹号。

### 8.2 文案结构

优先采用：

> 当前状态 → 必要说明 → 下一步动作

允许示例：

- “连接已建立。现在发送一条测试 Signal。”
- “收到新的 Signal，正在等待设备接收。”
- “还没有送达。先检查设备注册。”
- “需要你批准，才能切换到 Hosted。”
- “连接已恢复，Signal 继续送达。”
- “已送达。”

禁止示例：

- “我保证一定送到！”
- “你今天还没有连接项目哦！”
- “别让我失望，快打开通知。”
- “太棒了！又收到一条消息！”
- “我看到了你的付款数据。”
- “放心，Bellwire 什么数据都不会收到。”

### 8.3 语言准确性

- 使用具体状态词：已连接、已接受、等待批准、正在投递、已送达。
- 不把“服务端已接受”写成“手机已收到”。
- 不确定时明确写出不确定，并提供可执行检查项。
- 不责怪用户，不写“你没有正确配置”。
- 中英文版本保持同一事实强度；英文不得把 `accepted` 擅自翻译成 `delivered`。

## 9. 与现有 UI 的结合

冠羽鸟是品牌层和状态层，不是每个页面都要出现的装饰。Bellwire 使用 [UI 重构总纲](./ui-redesign-blueprint.md) 定义的 Signal Indigo + Amber Yellow 主题，同时继续保持安静的原生层级和项目内容优先。

### 9.1 尺寸层级

| 层级 | 尺寸 | 典型场景 |
| --- | ---: | --- |
| Hero | `88–104 pt` | Welcome / 首次引导 |
| Feature | `56–80 pt` | 通知说明、连接流程、真正的全局空状态 |
| Context | `32–48 pt` | Home 状态区、项目连接入口 |
| Micro | `16–28 pt` | 仅限经过专门简化的品牌头部标记 |

同一屏幕最多出现一只。除 Welcome Hero 外，角色不能成为页面最大视觉元素。

### 9.2 屏幕使用矩阵

| 场景 | 规则 | 推荐状态 | 说明 |
| --- | --- | --- | --- |
| Welcome | 必须出现一次 | `idle` → `listening` | 作为品牌 Hero，动作完成后静止 |
| 通知权限预说明页 | 可以出现 | `listening` | 只在系统弹窗之前说明用途；系统权限弹窗出现后保持静止，拒绝时不表现失望 |
| Home | 条件出现 | `listening` / `all_quiet` | `all_quiet` 只用于零项目或从未有事件；普通零未读不使用角色；有内容时退场 |
| Projects 真空状态 | 可以出现 | `all_quiet` | 指向“连接项目”的下一步，不替代项目头像 |
| Events 从未有事件 | 可以出现 | `all_quiet` | 筛选结果为空时不出现，以免反复卖萌 |
| 绑定与连接流程 | 可以出现 | `connecting` / `testing` | 不遮挡绑定码、按钮或技术说明 |
| Hosted 请求列表或批准前说明 | 可以出现 | `awaiting_approval` | 只提示“需要你决定”；进入最终同意与数据路径确认界面后退场 |
| 连接确认 | 可以出现一次 | `connected_verified` | 只按第 6.2 节的证据触发；不代表通知送达 |
| 普通项目列表 | 不出现 | — | 项目 Logo 和内容优先 |
| Project / Event 详情 | 不出现 | — | 信息密度和可诊断性优先 |
| Settings 常规区域 | 不出现 | — | 账户、设备、法律和配置保持原生、安静 |
| 购买、订阅、恢复购买 | 不出现 | — | 不用角色制造情绪性销售压力 |
| 删除、隐私、危险操作 | 不出现 | — | 后果、权限和明确文案优先 |
| Widget / Live Activity | 默认不出现 | — | 有真实 Surface 时项目 Logo 和数据优先；日后需单独审批 Micro 资产 |
| 系统通知 | 不插入角色 | — | 标题、正文和附件优先表达项目及事件 |

### 9.3 项目 Logo 优先级

1. 项目详情、事件、Surface、Widget 和 Live Activity 中，项目 Logo 永远拥有最高视觉优先级。
2. 冠羽鸟只代表 Bellwire，不能作为缺失项目 Logo 的占位符。
3. 项目没有 Logo 时，继续使用项目图标或首字母降级方案。
4. 同一卡片已有项目 Logo 时，角色不再出现在标题、角标或 Badge 内。
5. 不让角色抱住、遮挡、骑乘或装饰项目 Logo。

### 9.4 严肃场景禁区

以下场景角色完全退场：

- 删除账户、删除项目、清除历史等不可逆操作。
- 购买、恢复购买、账单和退款。
- 系统权限弹窗、隐私授权、服务条款和最终数据路径确认；通知权限预说明页与 Hosted 批准前说明页除外，但进入实际确认界面后角色必须退场。
- 严重生产事故、安全事件或数据丢失。
- 额度耗尽、设备不可用和投递失败的主要错误信息。
- 用户必须完整阅读技术说明的诊断页面。

不能用哭泣、冒汗、受伤、昏倒、庆祝、皇冠或卖萌文案弱化这些场景。

## 10. Private-first 表达边界

Bellwire 的默认 Private 路径见 [ADR-0004](../architecture/0004-private-direct-connections.md)。冠羽鸟只表达“状态发生变化”，不表达“它拿到了业务内容”。

正确表达：

- 它可以观察连接、等待 wake、看向真实状态文字或在批准边界前停下。
- Private / Hosted 必须同时用文字标注，不能只靠姿态、颜色或图案区分。
- Hosted 切换只有用户批准后，才可表现为继续推进。
- 角色动作只反映 App 确实知道的状态。

禁止表达：

- 鸟嘴衔信、背包、包裹、卷轴或业务内容卡片。
- 鸟把订单、邮件、金额或事件正文带入 Bellwire Cloud。
- 鸟打开、阅读、偷看或评论内容。
- Private 与 Hosted 共用一条没有边界说明的内容路径。
- 未完成 Direct 连接时表现为顺利送达。
- 使用“Bellwire 完全不接收任何数据”“绝对匿名”等超出事实的承诺。

## 11. 无障碍

- 纯装饰角色使用 `accessibilityHidden(true)`。
- 当角色对应未读、连接、异常或成功状态时，必须同时提供可读文字和控件的 `accessibilityLabel`。
- 不得只靠冠羽角度、表情、动作或颜色传达状态。
- 吉祥物本身不单独成为点击目标；如果它位于按钮内，按钮点击区域至少为 `44 × 44 pt`。
- Dynamic Type 达到辅助功能字号时，角色可移动到文字上方、缩小或隐藏，不能挤压主要文案。
- 浅色和深色背景都要检查头、喙、冠羽和翼的轮廓对比。
- VoiceOver 朗读产品状态，不朗读“鸟在抬头”“鸟很开心”等装饰性描述。

## 12. App Icon 规则

V1 构图已作为真机预览替换当前 `AppIcon.appiconset`，最终生产批准仍为 `SETUP_REQUIRED`。以下边界已经锁定：

- 使用冠羽鸟的头部与上半身特写，不塞入完整站立角色。
- 固定朝右，使用 `listening` 冠羽状态，三根全部清晰可见。
- 不加入文字、铃铛、手机、Wi‑Fi、通知角标、空心圆、连接线或场景。
- 不预制系统圆角，不加外边框和厚重投影。
- 主体建议占画布 `72%–76%`，喙与三根冠羽全部位于安全区。
- 先在 `1024 × 1024` 母版完成，再验证 `180 px`、`120 px`、`60 px` 和 `29 px`。
- Default、Dark、Clear 和 Tinted 外观必须保留同一核心轮廓；不能为不同外观重新生成不同的鸟。
- 当前 Apple 工具链支持用 Icon Composer 的同一分层文件标注 Default、Dark 和 Mono。采用它时，系统材质只作用于交付层，不能借机改变冠羽、喙、眼和头身结构。
- 现有 `AppIcon.appiconset` 可以作为迁移前的兼容路径；是否切换到 Icon Composer 由正式 Icon 定稿时的 Xcode 与最低系统版本共同决定。
- 扁平营销图、App Store 资产格式和透明通道要求在实际发布前按当时的 Xcode/App Store 校验器复核，不把会变化的平台提交规则冻结成角色结构。

平台参考：[Apple App icons HIG](https://developer.apple.com/design/human-interface-guidelines/app-icons) 与 [Icon Composer](https://developer.apple.com/icon-composer/)。

## 14. AI 生成合同

### 14.1 固定解剖提示词块

任何 AI 生成提示词都必须原样包含以下结构约束，再按用途追加第 14.2 节的视角合同：

```text
Original Bellwire crested signal bird, soft friendly matte editorial illustration,
warm amber head and back, warm cream chest, graphite beak and patterned wing,
long slim slightly down-curved beak. EXACTLY THREE rounded leaf-shaped crest
feathers, all three
separately visible with clear negative space in every pose: one long primary crest,
one medium crest at 80-85% of the primary length, one short low crest at 60-70%.
The same body proportions, same beak length, same fixed wing pattern and same
five-color Bellwire palette in every image. Quiet, reliable and restrained.
No text and no unexplained symbols.
```

负面约束必须包含：

```text
Never two or four crest feathers; no merged or hidden crest; no floating circles,
dots, rings, cables, signal trails, envelopes, letters, cards, parcels, backpack,
bell, crown, clothing, speech bubble, eyebrows, blush, human hands,
photorealistic feathers, plush toy, clay, plastic, glossy 3D, neon colors,
confetti, watermark or imitation of an existing mascot.
```

### 14.2 视角合同

#### A. 正式生产姿态

用于 App、Icon、官网和营销交付时，追加：

```text
Right-facing gentle three-quarter view, exactly one visible round eye and one
complete near-side wing. Production pose, not a turnaround sheet. No second eye.
```

#### B. 内部结构参考

仅用于 model sheet 的正面、侧面和三分之四面校准时，追加：

```text
Internal orthographic character turnaround for structural reference only: front,
right profile and right three-quarter views aligned to the same scale. The front
reference may show two anatomically placed eyes; production side and three-quarter
assets must show one eye. EXACTLY THREE crest feathers remain separately visible
in every view. No perspective distortion and no action pose.
```

正面双眼图只能放在内部 model sheet，不能导出为 App Icon、应用内角色或营销标准姿态。

#### C. 反向版式

需要角色朝左时，不重新生成。必须把已经批准的矢量结构母版整体镜像，再人工检查三根冠羽、眼、翼和光照。App Icon、应用内品牌标记和字标组合仍禁止镜像。

### 14.3 生成流程

1. 先生成单一标准姿态，不同时要求多动作。
2. 对照本文件逐项验收结构。
3. 通过后由同一结构母版派生其他姿态；不能分别“凭感觉”重画。
4. 所有状态图并排进行轮廓、冠羽、喙、翼纹和颜色对比。
5. AI 图只作为草案；正式资产由可编辑结构母版导出。

### 14.4 验收清单

任一项失败即拒绝，不能用“整体很可爱”抵消结构问题：

- [ ] 冠羽恰好三根，三根均完整且分别可辨认。
- [ ] 主、中央、低位冠羽的长度关系固定，没有融合或隐藏第四根。
- [ ] 所有状态使用同一头身比例，关键比例误差不超过 `±5%`。
- [ ] 喙长度、弯曲方向和粗细一致。
- [ ] 正式生产姿态朝右，只显示一只眼和一只完整近侧翼；内部正面结构参考是唯一双眼例外。
- [ ] 翼固定为一个石墨肩部、一道奶油横带和三枚石墨飞羽瓣。
- [ ] 尾始终为两枚，未随机增加羽毛或条纹。
- [ ] 色值来自固定色板，角色没有被语义色整体染色。
- [ ] 风格保持柔和哑光，没有硬描边、厚纸片阴影、塑料感或写实羽毛。
- [ ] 没有信封、卡片、背包、服装、皇冠、铃铛或人类手势。
- [ ] 没有无意义圆圈、光点、拖线、波纹、火花或装饰符号。
- [ ] 姿态属于官方状态库，动作没有改变身体结构。
- [ ] 缩到 `64 px`、`40 px`、`29 px` 后，三根冠羽和长喙仍可识别。
- [ ] 转为单色剪影后，仍能凭三根冠羽和长喙识别。
- [ ] 图中没有文字、水印、签名、伪 Logo 或与现有品牌高度相似的造型。
- [ ] 正式交付已从干净、可编辑的母版导出，不是直接使用 AI 位图。

## 15. 禁止变体

出现以下任一情况，即不属于 Bellwire 官方角色：

- 冠羽不是三根，或三根长度关系改变。
- 冠羽变成头发、耳朵、天线、火焰、皇冠或 Wi‑Fi。
- 在正式侧面或三分之四生产姿态中使用第二只可见眼；内部正面 model sheet 是唯一例外。任何姿态都禁止白色眼球、眉毛、睫毛、腮红或大嘴。
- 喙变成鸭嘴、鹰钩、鹦鹉喙或短鸡嘴。
- 翼纹、尾羽数量或头身比例在不同素材中随机变化。
- 增加帽子、围巾、衣服、鞋、手套、背包或职业制服。
- 增加人类手掌、手指、牙齿或肌肉。
- 改成猫头鹰、狐狸、小鸡、企鹅或通用圆鸟。
- 使用毛绒、黏土、玻璃、金属、塑料玩具或写实摄影质感。
- 使用非官方主体色或用颜色区分会员等级。
- 在身体上印字母、铃铛、闪电、聊天气泡或其他 Logo。
- 为不同功能创建不同物种、年龄、服装或“升级形态”。
- 用无意义圆圈、拖线或粒子假装产品状态。
- 直接模仿其他产品的吉祥物轮廓、表情或动作系统。

## 16. 治理与变更规则

1. 任何人都不能用一张新生成图覆盖本文件的设定。
2. 角色结构、色板、人格、状态语义或严肃场景边界发生改变时，必须先更新本文件并提升版本号。
3. 一次变更必须同时检查 App Icon、应用内资产、Widget、官网、商店素材与文案，不能只修一个页面。
4. 正式矢量母版完成后，将几何测量值补回本文件；母版不能自行改变“三根冠羽”等锁定规则。
5. 新动作必须映射到一个明确产品状态，并说明触发事实、结束状态和 Reduce Motion 方案。
6. 新道具默认不批准；确有产品必要性时，必须证明不会暗示角色读取或携带 Private 内容。
7. 对外正式名字仍为 `TBD`。名字确定前，代码、埋点和资产统一使用 `Mascot`，不散落临时昵称。

## 17. 落地前质量门

在任何角色资产进入生产前，负责人需要确认：

- [ ] 已通过第 14.4 节的全部视觉验收项。
- [ ] 角色状态与真实后端/设备事实一致，没有提前表达成功。
- [ ] 页面确实属于第 9.2 节允许的场景。
- [ ] 同屏不超过一只，且没有压过项目 Logo 或主要操作。
- [ ] 没有无归属圆圈、光点、拖线或其他装饰符号。
- [ ] 提供了等价文字、VoiceOver 标签和 Reduce Motion 行为。
- [ ] 浅色、深色、Dynamic Type 和目标尺寸均完成视觉检查。
- [ ] 资产来自同一结构母版，未直接交付 AI 位图。
- [ ] App Icon 已单独通过全部目标尺寸和安全区检查。
- [ ] 若修改锁定项，本文件已同步升级版本。
